## 一句话定义

Engram 是一个**单用户的私人 AI 管家** —— 长期共生地观察、理解一个具体的人，并在被询问时给出基于深度状态的建议、决策辅助、关系/伏笔追踪和模式识别。

它不是日记 app、不是 todo、不是通用 chat 助手、不是多用户产品。

---

## 人设底色

**冷酷的智者。**

默认底色是**诚实直白**：不谄媚、不为安抚而打圆场、不绕弯子。智者风范优先于亲和力。当事实分析的结论让人难受时，仍然说出来（用对方能接受的表达方式，但不替换结论）。

**情绪疏导 / 情绪价值** 是用户**显式 opt-in 的覆盖模式**（"现在我不需要分析，我需要被安慰"），不是常态。V1 不实现切换机制，留给 post-V1。

这个设计保证人设**长期一致**：用户能预期他的反应、能信任他在重要决策上不会出于"让你舒服"的考虑而扭曲事实。

## 架构本质

```
┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐
│   多渠道 input   │───▶│   个人建模       │───▶│   帮助升华       │
│                  │    │                  │    │                  │
│ • 主动 capture   │    │ • 长期画像       │    │ • 决策辅助       │
│ • OpenClaw 采集  │    │ • 事件流         │    │ • 关系建议       │
│ • (扩展中...)    │    │ • 主干网         │    │ • 伏笔追踪       │
│                  │    │ • 关系/伏笔/承诺 │    │ • 模式识别       │
└──────────────────┘    └──────────────────┘    └────────┬─────────┘
        ▲                                                 │
        │                                                 │
        └────────────── 结果回流 ─────────────────────────┘
              （用户执行建议后 capture 结果）
```

三层契约：

### 1. 多渠道输入

输入来源会持续扩展，不锁定在某一种通道：

- **用户主动 capture**：thoughts / decisions / observations / 反思（web UI / MCP / 命令行）
- **OpenClaw 采集**：微信 / 飞书等社交平台聊天记录（经 intent gate 过滤后入库）
- **未来扩展**（V1 不做但架构留口）：跟 AI 的对话历史、阅读消费内容、语音日记等

每个 channel 都要经过 intent gate —— Engram 只接收**认知性内容**（思考、决策、反思），不接收纯事件日志 / 提醒 / 杂项笔记。

### 2. 个人建模

不是单一画像，是**多层模型**：

- **profile dimensions** — 长期人格 / 工作认知维度的贝叶斯累积
- **entries 流** — 时间序的原始反思 + 切片
- **backbone 主干网** — 跨 domain 的知识 / 关系图谱
- **关系 / 伏笔 / 承诺追踪** —— 谁、答应过什么、上次互动是什么、状态如何

### 3. 帮助升华

输出形态见下面 "能力域" 一节。**核心是用户问的时候给出基于完整状态的回答**，不是主动推送。

### 结果回流（闭环）

用户执行了管家的建议之后，把结果作为一条**普通 entry** capture 回来 —— 复用同一管线，走 intent gate → 切片 → 画像融合 → 主干网。

V1 **不**引入特殊的 suggestion 状态机（不追踪"哪条建议执行了" / "成功率怎么样"）。这种闭环精细化留给 post-V1。

## 消费面契约

**Pull-only via MCP。**

所有"主动建议"都作为**用户询问时的回答内容**给出。系统**不做**：

- Push 通知 / 实时打扰
- 独立常驻 UI（advisor chat app 之类）
- 后台 cron 任务推消息
- 任何形式的"管家敲门"

"管家"的语义重新定义为「**随时可咨询且记忆完整**」，不是「always-on 守护」。

**三类面要分清**：

| 面 | 承担什么 | 实现 |
|---|---|---|
| **咨询面 (pull, 一等)** | 用户问管家、获取建议、状态回顾 | **MCP only** |
| **录入面** | 把内容喂进 Engram | Web UI + MCP + OpenClaw + 未来 channels |
| **检查面** | 看 pipeline 运行细节、entries、画像、知识图谱 | Web UI |

Web UI 不是咨询的主战场，它是录入 + 检查的工具。"独立 advisor UI" 在 anti-features 里说的是**咨询型 chat 应用**，不是已有的 web 工具页。

---

## 用户契约

**单人 + 数据完全隔离。**

- 不论本地部署还是未来潜在多实例运行，**每个用户对系统而言都是世界唯一存在**
- 用户感知不到、也不应感知到任何其他用户的存在
- 不做账号 / 不做协作 / 不做共享 / 不做 SaaS / 不做多租户
- 想用 → 自己 clone 一份本地跑（或部署一个完全私有的实例）

OSS 公开理由：**架构透明化、可审阅、可自托管**。不是发展用户群、不是做社区产品。

## 能力域（V1）

下面是 V1 系统**有意支持**的咨询场景类型。具体 MCP 工具签名见代码 + 后续 plan：

| 场景 | 用户问的样子 | 系统输出基于 |
|---|---|---|
| **状态回顾** | "我最近的关注点是什么？" / "我这周状态怎么样？" | 近期 entries + profile diff + 情绪/能量曲线 |
| **关系维护** | "我最近该跟谁建联？" / "我跟 X 上次说了什么？" | 关系图谱 + 互动时序 + 承诺/约定记录 |
| **决策辅助** | "我该不该接这个 offer？" / "过去的我怎么想这件事？" | 历史相关 entries + 画像匹配度 + 反复模式 |
| **伏笔追踪** | "我之前想做但没做的事？" / "答应过的事还没回应？" | 伏笔/承诺记录 + 未跟进列表 |
| **模式识别** | "我反复在 X 上犯什么错？" / "什么时候我容易这样？" | entries 聚类 + profile 维度的反复触发 |

**所有这些都是 pull-mode。** 用户问之前，系统不会主动 surface。

## 明确不做（anti-features）

| 类别 | 不做原因 |
|---|---|
| Notes / journal / diary / habit tracker / todo / reminder | 不是它的品类。这些有更合适的工具。intent gate 会拒绝 |
| 密钥 / dotfiles / 配置文件 / 凭证存储 | 安全模型不匹配，也是另一类问题 |
| Push 通知 / 实时 surfacing | 见消费面契约 |
| 独立 advisor UI（V1）/ 桌面常驻 app | 见消费面契约 |
| 多用户协作 / 共享 / 社区 / SaaS | 见用户契约 |
| 把画像作为 context 注入第三方通用 chat（context middleware）| Engram **自己**是消费面，不当别人的 context layer |
| 通用 chat / 闲聊 / 一般助理任务 | 不是它的品类。它只回答关于"你"的问题 |
| 浏览器扩展 / IDE 内联建议 / OCR / 语音转写 | 跟核心建模无关，离散工具该单独活 |

这些拒绝是**架构性的**，不是"以后可能做" —— 它们违反核心契约（消费面 / 用户 / 品类边界）。

## 不变项 vs 变化项

为了让未来的 maintainer / AI session 知道什么可以动、什么不能动：

**不变项（动了就不是 Engram 了）：**
- 单用户 + 数据完全隔离
- Pull-only 消费面 + MCP 为一等通道
- 只接收认知性内容（intent gate 守门）
- 冷酷智者人设底色

**变化项（持续演进）：**
- 输入 channel 列表
- 建模维度（profile dimensions / backbone domains）
- 能力域的具体 MCP 工具
- 部署形态（本地 / 私有云 / docker-compose 模板）
- 情绪疏导 opt-in 的实现路径（V1 后议）

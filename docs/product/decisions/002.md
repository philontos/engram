## Context（背景）

ADR-001 锁定了"私人认知副脑"的方向，但消费侧具体走哪条通道没有定。摆在桌面上的形态包括：独立 web/移动 app、浏览器扩展、IDE 插件、MCP server、邮件/微信推送。每一条都有工程成本和注意力成本。

两个事实拉紧了选择空间：

1. **主用户日常工作大量时间在 Claude Code / Codex / Cursor 里。** 这些客户端原生支持 MCP。
2. **`cognitive-mcp` 已落地并在使用**（stdio，注册到客户端配置中，已有 `cognitive_capture_thought` + `cognitive_query`）。基础设施在。

如果消费走 MCP，**Engram 的"私人智囊"角色直接寄生在用户已有的工作流里**，零新增上下文切换；如果另起独立 UI，必须先解决"为什么打开它"的问题——而 dogfooding 指标是本项目的硬指标（见 ADR-001）。

## Decision（决策）

V1 把 **MCP 作为唯一的一等消费通道**：

- 通过 `cognitive-mcp` 暴露新工具集，让 Claude Code / Codex / Cursor 等 MCP-aware 客户端**直接担任** Engram 的对话与咨询界面。
- **V1 不建独立的 advisor 聊天 UI**。
- 现有 frontend 的 `ProfileTab` 重做为"事实 + 叙事"形态，但**降为后台自审界面**（P1），不是日常消费主面。
- 周报通过外部推送（邮件 / 微信，由现有 OpenClaw / 邮件 cron 担任），同样不需要新建独立 UI。

### V1 暴露的 MCP 工具集

| 工具名 | 输入 | 输出契约 | 触发场景 |
|---|---|---|---|
| `cognitive_capture_thought`（已有） | 用户原话 | 返回 entry id | 用户显式说"记下" |
| `cognitive_query`（已有） | 自然语言问题 | 流式 NDJSON，含 cite | 用户找答案/反思 |
| `engram.who_am_i`（新） | （无） | 人话叙事 + facts 摘要，**强制 cite** 维度 + entry | "给我一份现在的我" |
| `engram.recent_patterns`（新） | window: N 周 | 反复 blocker / decision pattern 列表，每项带证据条目 | "我最近又在重复什么模式" |
| `engram.review_decision`（新） | 决策描述 | 引用对应维度 + 历史相似 entry，必须给出**仅对此用户成立**的视角 | "我在考虑 X，帮我审视" |
| `engram.weekly_report`（新） | （无） | 当周合成报告（同周报 job 内容），按需触发版 | 用户主动复盘 |
| `engram.what_should_i_practice`（新） | （无） | 基于 strengths/gaps 给突破方向 | "我该练什么" |

### 输出契约：所有派生建议必须 cite

每个 `engram.*` 工具的返回**必须**包含：

- 至少一个**画像维度**引用（namespace + 子维度 + 当前 score/τ）
- 至少一条**源 entry id** 作为证据

无 cite 的输出由 MCP 层直接拒绝并要求 LLM 重生成。这是和通用 chat 的硬性差异化护城河。

### 采集 / 查询边界保持

MCP 工具调用**不会**把当前对话内容自动写入 entry 库（沿用既有的"采集 / 查询分离"纪律：query 期间不静默写，仅通过 `suggest_capture` 提示用户一键确认）。**绝不静默写。**

## Consequences（后果）

**锁定的事：**

- `cognitive-mcp` 成为 V1 用户感知最重的一层，工具契约稳定性是高优。
- 新工具开发优先级 > 任何 UI 工作。
- 输出 cite 校验逻辑必须在 MCP 服务端做（不靠 LLM 自律）。
- 未来若要支持非 MCP 客户端的人（含未来给别人用），需要在更上层包一层 HTTP API；现在不做。

**关闭的可能：**

- V1 不投资移动端独立 app、桌面独立 app、浏览器扩展、IDE 内联补全。
- 不为 Engram 单独建立 chat session 概念（沿用 MCP 客户端的会话模型）。

**可接受的副作用：**

- 强绑定 Claude Code / Codex / Cursor 的 MCP 支持。如果某一天 Anthropic 改 stdio 协议或 MCP 演进有 breaking change，用户需要跟。
- ProfileTab 看到的人会少（只在自审时才打开）—— 没关系，它不是 hero 面。

## Alternatives considered（被考虑的替代方案）

1. **独立 web advisor app（替代 ProfileTab，做成主入口）。**
   被拒。建一个新的"还要打开"的入口违背 dogfooding 现实——用户不会专门为它腾出位置。同时复制了 Claude Code 已经做得很好的对话能力。

2. **浏览器扩展，悬浮在任意网页上提供"问 Engram"按钮。**
   被拒。工程量重（多浏览器适配、CSP、权限申请、签名分发），且用户主要工作在终端/IDE 而非浏览器。优先级在浏览器原生对话场景出现后再评估。

3. **HTTP API + 命令行 `engram` CLI。**
   暂缓。比 MCP 更通用，但失去了客户端原生对话上下文。作为 V2 选项保留，特别是在需要从非 MCP 环境（脚本、CI、自动化）调用时考虑。

4. **保持现状（只暴露已有两个工具）+ 把消费写在 ProfileTab 里。**
   被拒。已有两个工具不足以承载"周报、反复模式、决策审视"等具体场景；把这些塞进 ProfileTab 又回到了"得专门打开 app"的死路。

## Notes

- 工具命名前缀 `engram.*` 是**临时约定**。如果 MCP 生态对工具命名空间有共识标准（例如反向域名）出现，统一对齐。
- 重新评估触发条件：如果 4 周内用户发现自己更多在"想问但工具不够用"，写 ADR-002a 扩工具集；如果发现**没人想用任何新工具**，回头审视的应该是定位（ADR-001），不是工具数量。
